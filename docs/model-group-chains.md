# 按模型分组链

## 使用方式

在 API Key 的分组链管理中，新建时选择“按分组”或“按模型”。现有链继续按分组运行；链保存后不能变更类型，需要新建另一条链再重新绑定 Key。

按模型链的每一行选择一个分组及该分组内的一个或多个模型，行顺序就是跨组重试顺序。例如 A 组选 X、Y，B 组选 X、Z：请求 X 时依次尝试 A、B；请求 Y 时仅尝试 A；请求 Z 时仅尝试 B。不会把请求模型自动换成另一个模型。

- 每人最多 10 条链，每条最多 10 个不重复分组，每行最多 100 个模型，规则 JSON 最多 60 KiB。
- 仅可选择用户静态授权且配置了倍率的普通分组；不包含 auto、其他链或仅靠活动授权的分组。
- 可用目录是每一行“已选模型 ∩ 本行分组当前启用模型”的并集，空结果不会回退到全组目录。
- Key 的模型映射先执行，再以映射后的模型匹配链规则。仅沿用已有的特定模型标识归一化，不自动把任意日期版本视作同一模型。
- 任一分组失权时拒绝整条链；模型下架只移除对应行的可用模型。后续请求使用更新后的配置。
- 实际使用的分组继续决定该次请求的计费倍率；不改变模型计费算法。

## 与跨模型兜底的关系

按模型链不允许启用 API Key 的独立跨模型兜底。新建、完整编辑和表格快速换组都会校验最终状态，冲突时拒绝保存，不会静默关闭开关。应先关闭跨模型兜底，再绑定按模型链。已禁用的兜底配置保留为草稿，切回普通分组也不会自动启用。

运行时也禁止按模型链加载跨模型兜底。管理员指定渠道和 Playground 的分组覆盖不能绕过链规则；内部已校验渠道的重试仍可正常执行。

删除按模型链后，绑定 Key 回退到用户所属分组，关闭跨组重试及跨模型兜底，保留禁用的兜底草稿。按分组旧链的删除行为保持不变。

## API 兼容

接口路径和 chain:<id> 绑定格式不变，继续使用 user_group_chains 表。新增 type 字段与 TEXT 类型 items 列，历史空 type 按 groups 解释。旧的 {name, groups} 创建、更新请求仍有效。按模型链使用 {name, type: "models", items: [{group, models}]}，其中 groups 由 items 顺序派生；若同时传 groups，必须完全一致。

GET 链列表新增 type、items、max_models_per_item、max_items_bytes。用户分组目录新增 chain_selectable；链条目增加 chain_type、chain_items 并保留 chain_groups。POST、PUT、DELETE 的既有响应结构不变。模型目录支持 /api/user/models?group=chain:<id>，仍按所属用户授权。

## 发布和回滚

1. 备份数据库，先升级全部后端节点；自动迁移新增普通文本列，无需数据库专用 JSON 类型。
2. 确认所有后端节点均支持模型链后，再发布前端并允许创建模型链。不能在新旧后端混用时创建模型链。
3. 发布前运行相关 Go、前端行为测试、类型检查、lint、格式检查和生产构建；分别在 SQLite、MySQL、PostgreSQL 上验证迁移与读写。未提供实例的数据库必须明确记录为未验证。
4. 回滚到不识别模型链的版本前，先停用所有模型链绑定 Key，完成解绑或迁移并验证后再回滚。旧版本会只读派生的 groups，可能意外扩大模型访问范围，因此不能直接带着模型链配置回滚。

保留 new-api / QuantumNous 项目标识；本功能不改动 relaykit 模块或既有计费算法。
